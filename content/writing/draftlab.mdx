The goal of this project was to see how much of a coding agent’s output a smaller model can predict, and whether those predictions can save generation time. The experiments use traces from the local agent loop.

A language model normally generates one token at a time, where a token can be part of a word, some punctuation, or a piece of code. Each new token depends on the previous ones. With speculative decoding, a cheaper model drafts a few tokens and the target checks the block in one call. We get more tokens out of that call when the drafts are accepted, although we also have to pay for drafting them.

Our local Qwen 27B coding agents supply the traces, including thinking, text, code, and tool traffic. **The experiments here use 1.5B and 0.5B targets**, so they do not measure a speedup of the original 27B agents.

On October 6, an audit corrected sampling, cache handling, and confidence intervals. The figures below use the corrected held-out results and judge rerun, alongside the unfinished sweep. Earlier speedup claims need a controlled comparison.

Qwen2 runs in JAX, with grouped-query attention, rotary positions, RMS normalization, a gated MLP, and a fixed-size key/value cache. Adapters trained in PyTorch are merged into the JAX weights for generation.

Requests go through a Go gateway that handles API keys, rate limits, routing, and a circuit breaker. It streams output and exposes Prometheus metrics. Grafana displays latency, token counts, acceptance, and backend health.

Dockerfiles, a Helm chart, a host-only kind check, and Terraform/GKE configuration are included in the repo. This snapshot has no production deployment or GPU performance results.

## Speculative Decoding

The draft has to be checked in a way that preserves the target’s output distribution. Otherwise the smaller model changes what we generate.

Call the target’s next-token distribution `p`, and the distribution that produced the draft `q`. A proposed token `x` is accepted with probability `min(1, p(x)/q(x))`. At the first rejection, we sample a replacement from the normalized `max(0, p − q)` and discard the rest of the block. If every draft passes, we sample a bonus token from the target.

At temperature zero, we keep a draft if it matches the target’s top choice. For sampling, the acceptance and replacement rule preserves the target distribution, so two runs can produce different text. The rule comes from [Leviathan et al., 2023](https://proceedings.mlr.press/v202/leviathan23a.html) and [Chen et al., 2023](https://arxiv.org/abs/2302.01318).

<DraftlabStep />

Drafts after a rejection were predicted using a token we have discarded, so they are discarded too. A fully accepted block can emit `k + 1` tokens, subject to the output limit.

The target cache holds all the committed tokens except the newest one. That newest token stays pending, so the next call sends `[pending_token] + drafts` together. Logit row `j` predicts draft `j`, and the last row predicts the bonus. After accepting `A` drafts, we keep the pending token and accepted prefix in the cache, then the replacement or bonus becomes the next pending token.

Rollback changes the cache’s logical length without recomputing the prefix. Old values can stay in the buffers as long as the attention mask hides them, and the drafter’s cache must match the committed history too. The pending-token setup removed a second target call that used to process the bonus separately. See [`1e9f5d3`](/writing/draftlab/report.html#commit-sampling).

Triton verify and alpha kernels have PyTorch references. The alpha evaluator can use the fused kernel on CUDA; the JAX decoder currently verifies drafts in its own loop.

## The Data

The corpus is split into thinking, text, fenced code, tool calls, and tool results. Duplicate blocks are removed, and blocks are capped at 4,096 tokens. Each whole run stays in one split, which keeps adjacent parts of a session from crossing between training and evaluation.

The first validation and test splits each had three runs, with one run contributing most of their tokens. The newer hold-out adds 14,974 blocks and 4.24 million tokens across 14 later runs. It excludes runs already present and exact `(kind, text)` duplicates from the older splits.

<DraftlabCorpus />

Source: `results/corpus_stats.json`. Tool results are things the agent reads, so being able to predict them does not directly save time generating the agent’s own output.

The alpha evaluation uses 700 held-out blocks and scores 56,990 token positions. Blocks are selected across runs, capped at 256 tokens, and given context from preceding selected blocks within a 1,024-token budget. At each position we give both models the recorded prefix and compare their predictions. This is teacher forcing, where the recorded tokens determine the history.

Alpha measures the overlap between their probability distributions:

`α = Σₓ min(p(x), q(x)) = 1 − TV(p, q)`

An alpha of 0.71 means about 71% of the probability mass overlaps on average across these positions. With correctly sampled proposals at those contexts, it gives expected acceptance. It is different from next-token accuracy against the recorded trace, and does not predict how much of every live draft block will pass.

The saved estimates average 1,000 bootstrap replicates. Each replicate samples whole runs with replacement and pools their token counts, keeping related parts of a session together. Larger runs still contribute more tokens.

Alpha here uses unscaled softmax, or temperature 1. The sweep uses temperatures 0 and 0.7, a different target, and generated continuations. The selected alpha blocks also contain no code row. These results apply to the sampled agent traffic.

### DPO still has a problem to fix

The DPO pair builder chooses `d = argmax(q)`, then applies an acceptance test using the soft probability `q[d]` and residual `p − q`. Since the token was chosen greedily, those probabilities do not describe how it was produced. The code also prefills a sequence and feeds its last token again when starting cached generation. These findings come from `draftlab/drafters/dpo.py`, which the October 6 decoder fix did not change. Training has not been rerun, so the pairs need checking and rebuilding before the DPO increase can support a claim about this method.

## Generation and Timing

The corrected sweep generates 32 tokens after short held-out prompts, with draft lengths `k ∈ {1, 2, 4, 8}` and temperatures 0 and 0.7. Its Qwen2.5-0.5B-Instruct target is about the same size as the learned drafter. The grid measures decoder behavior; a larger target would give a better comparison for the cost of a smaller drafter.

Each finished prompt is saved to a sidecar file and folded into Parquet when its cell finishes or restarts. The report reads both formats and removes duplicates by configuration and prompt index.

<DraftlabSweep />

Sources: `results/sweep.parquet` and its 8 saved sidecars. The target-only baselines, 1.5B sweep, and controlled speed benchmark are still pending in this snapshot, so we do not have a measured speedup to report yet.

Once generation diverges from the recorded trace, the next prediction sees a different history. Alpha on recorded prefixes cannot describe all of those later contexts. The accepted/drafted ratio also counts drafts after the first rejection, even though they cannot be committed, so changing `k` can change that ratio while first-token overlap stays the same.

The identity control uses the target itself as the drafter, where acceptance should be one. At `k = 8`, a full step emits nine tokens, but the 32-token output limit requires four steps. The average is therefore `32 / 4 = 8` tokens per step.

<DraftlabCost />

The model assumes constant, independent acceptance, a proposal at every position, and block verification costing the same as one target decode. It excludes prefill, output limits, EOS, compilation, cache work, and resource contention. [Leviathan et al., generated-token and wall-time analysis](https://proceedings.mlr.press/v202/leviathan23a/leviathan23a.pdf).

`tools/bench_speedup.py` warms up the model shapes, alternates configurations over repeated passes, and compares each with target-only decoding on the same prompts. Its result file, `results/speedup_bench.json`, was absent from this snapshot. Timings from concurrent sweep workers cannot establish the runtime saving.

## Checking the Output

The tests compare greedy output with the target, check the cache against a fresh prefill, check sampled distributions, and count target calls per step. Newer sampling tests use an identity drafter and check the second-token distribution of a mismatched drafter. A first-token test can miss incorrect state carried into the next step.

The judge rerun uses held-out prompts on the fixed engine, with a 0.5B-Instruct target, DPO drafter, `k = 4`, temperature 0.7, and 16 output tokens. The local `qwen-agent` judge receives blind comparisons in both orders, with cached responses and a 150-call cap. These are short-output preference checks, which do not measure completion of coding tasks.

<DraftlabJudge />

Source: `results/judge.json`, generated October 6. There were 150 calls used and 18 invalid responses, and the chart only counts included verdicts. The file’s order-disagreement rate includes invalid orders in its denominator; the counts separately show prompts with both orders valid.

The speculative-versus-target win-rate interval includes 50%, which does not establish equivalence or non-inferiority. Verdicts from both orders judge the same prompt and are correlated, while the saved Wilson intervals treat them as independent. Eight of the 39 prompts with both orders valid received conflicting judgments.

Distribution preservation depends on the acceptance rule and its implementation checks. The judge can help catch an obvious quality change in the short continuations.

At temperature zero, output should match the target’s greedy tokens. At positive temperature, its distribution should match target-only sampling within numerical tolerance. Statistical tests check a finite sample. The commit adding the new checks records that they fail on the old implementation; this report uses saved evidence rather than a fresh run of the full test suite.

## Fixing the Measurements

The commit history records several bugs that changed how the results had to be read.

### One token off

The evaluator compared token `i` with logit row `i`, which predicts token `i + 1`. The low overlap came from comparing the wrong positions.

The fix lines up logits with next-token labels and skips the first position when there is no preceding context. Tests compare cross-entropy with Hugging Face’s shifted loss and check repeated versus shuffled text.

[Code and test diff: 7a84891](/writing/draftlab/report.html#commit-alignment)

### The cache can still be wrong

The drafter decoded the last committed token twice, and its position marker failed to advance correctly when every draft passed.

The fix corrected proposal positions and rollback. Tests compare the drafter’s cache and next proposal with a fresh prefill after rejection and full acceptance. The October 6 change then moved to the pending-token setup described earlier.

[Code and test diff: ae371e3](/writing/draftlab/report.html#commit-cache)

### Sampling the drafts

Drafts were chosen greedily but reported with soft probabilities and without matching temperature. The acceptance test used a distribution that had not produced the token, biasing sampled output toward greedy choices.

Model drafts now come from `softmax(logits / T)`, and the verifier receives that distribution. At temperature zero, the proposal distribution is one-hot at the greedy token. The decoder sets the drafter’s temperature and seed. This change also removed the extra target call.

[Code and test diff: 1e9f5d3](/writing/draftlab/report.html#commit-sampling)

### Suspiciously small error bars

The bootstrap dimensions were swapped: `n_runs` replicates with `n_boot` draws each. Drawing so many times from the same few runs made their representation almost even in each replicate, collapsing the intervals around the estimate.

The corrected version makes `n_boot` replicates, each with `n_runs` session draws. A regression test uses two runs with very different acceptance rates and requires the interval to span both.

[Code and test diff: 0158d68](/writing/draftlab/report.html#commit-bootstrap)

### More tokens do not always mean more evidence

The first splits had few independent sessions. Selecting the first N prompts could concentrate a content type in one session, and the old speedup claims used timings from concurrent sweep workers.

The changes add a later hold-out, select prompts round-robin across runs, increase generation from 16 to 32 tokens, and add a 1.5B target option. The separate benchmark alternates configurations and includes target-only decoding.

[Code and test diff: 5f98414](/writing/draftlab/report.html#commit-heldout)

### Knowing when to stop

Serving kept generating after end-of-sequence tokens and returned `finish_reason: stop` even at the length limit.

It now stops at the tokenizer’s EOS markers, excludes them from completion text, and returns `stop` or `length` accordingly. A no-drafter model is also available for comparisons.

[Code and test diff: 48cf15b](/writing/draftlab/report.html#commit-serving)
