Hi! The goal of this project was to see how much of a coding agent's output a smaller model can predict, and whether those predictions actually save generation time. The data is my own: traces from the local Qwen 27B agents in my agent loop, split into thinking, text, code, tool calls, and tool results.

The experiments use 1.5B and 0.5B targets, so they measure the idea on agent traffic, not a speedup of the 27B agents themselves.

## How Speculative Decoding Works

A language model normally generates one token at a time. With speculative decoding, a cheap drafter guesses the next few tokens and the target checks the whole block in one call. Every accepted guess is a token we didn't have to generate one by one, but the guesses aren't free either.

The acceptance rule matters: a draft token `x` is kept with probability `min(1, p(x)/q(x))`, and the first rejection is replaced by a sample from what's left of the target distribution. That keeps the output distribution exactly the target's ([Leviathan et al., 2023](https://proceedings.mlr.press/v202/leviathan23a.html)), so speculation changes speed, not what the model says.

I built the target in JAX (Qwen2 with a KV cache that can roll back rejected drafts), three kinds of drafters, a Go gateway with metrics, and a Ray sweep over drafters, draft lengths `k`, and temperatures.

## 1. Agent Traffic Is Very Predictable, but Not Evenly

The main metric is overlap (α), the share of the target's probability mass the drafter agrees with at each position. It's measured on 14 later runs held out from training (56,990 positions), with confidence intervals that resample whole runs:

<SpeculativeOverlap />

A 0.5B model fine-tuned with LoRA on the agent traces overlaps with the target **71.2%** of the time. Plain n-gram lookup, which just copies what came earlier in the context, gets **32.3%**. A tiny model distilled from scratch gets 1.1%, so it's basically useless.

## 2. Predicting Isn't the Same as Being Fast

Overlap only says how often a guess is right. Whether that saves time depends on what the guesses cost, so I benchmarked each configuration head to head against plain decoding, in one process, on the same 34 held-out prompts, with the order interleaved across repetitions:

<SpeculativeSpeedup />

With the 1.5B target, LoRA drafting at `k = 2` is **1.58×** faster and n-grams at `k = 8` are **1.50×** faster. The interesting part is that **longer LoRA drafts get slower**: at `k = 4` each step emits more tokens (2.14 vs 1.86), but every extra draft token costs a full forward pass of the 0.5B drafter, so the speedup drops to 1.25×. N-grams cost almost nothing to draft, so they can afford long guesses even at 20% acceptance.

These are CPU numbers. On a GPU the target forward is memory-bound, so drafting is relatively cheaper and the best `k` should move up.

## 3. The Measurement Bugs Mattered More Than the Model

The first version of this report had numbers that looked great and were wrong. An audit of the code found six bugs, and each one changed how the results had to be read:

- **One token off.** The evaluator compared token `i` with the logit row that predicts token `i + 1`. ([7a84891](/writing/speculative-agent-workloads/report.html#commit-alignment))
- **Sampling wasn't lossless.** Drafts were picked greedily but scored with soft probabilities, which inflated acceptance at temperature 0.7 and pulled samples toward greedy output. ([1e9f5d3](/writing/speculative-agent-workloads/report.html#commit-sampling))
- **Error bars about 100× too narrow.** The bootstrap had its dimensions swapped, so a "significant" DPO gain disappeared once it was fixed. ([0158d68](/writing/speculative-agent-workloads/report.html#commit-bootstrap))
- **The cache, the timing, and the stop token.** The drafter decoded a token twice, speed came from concurrent sweep workers, and serving ran past the end-of-sequence token. ([ae371e3](/writing/speculative-agent-workloads/report.html#commit-cache), [5f98414](/writing/speculative-agent-workloads/report.html#commit-heldout), [48cf15b](/writing/speculative-agent-workloads/report.html#commit-serving))

The code fixes come with regression tests that fail on the old code, and the project's `REPORT.md` is now checked by a script that recomputes every number in it from the saved results. A blind LLM judge also found no quality difference between speculative and plain output (43% win rate, CI [33%, 54%]), which is what the acceptance rule guarantees.

## What Didn't Work

- **DPO on top of LoRA did nothing measurable**: 71.35% vs 71.20% overlap, with overlapping intervals. The pair builder also has a known bug, so this one needs a rebuild before it means much.
- **The distilled tiny drafter.** Its validation loss improved, but at 1.1% overlap it's well below the size where imitation starts to work.
- **Recorded text overstates live acceptance.** LoRA's 71% overlap on recorded traces becomes about 63% acceptance while generating, since the model's own output drifts away from what the drafter was trained on.

## Future Improvement
